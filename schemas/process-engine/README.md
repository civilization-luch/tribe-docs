# Схемы движка процессов

Машиночитаемые контракты движка процессов. Источник истины: этот каталог.

```
schemas/process-engine/
├── process-definition.schema.json   # схема определения процесса (v0.2)
├── examples/
│   ├── purchase.process.json        # эталонный процесс «Закупка»
│   └── README.md                    # решения и переменные процесса
└── README.md
```

## Что описывает схема

**Модель исполнения**, а не доменную модель и не контракт агента.

| Слой | Что описывает | Где живёт |
|---|---|---|
| Доменные схемы | агрегаты и события (`PurchaseLaunched`) | `schemas/<домен>/` |
| **Определение процесса** | паспорт, роли, данные, правила, состояния, переходы, таймеры, запреты, тесты | здесь |
| Агентные контракты | инструменты, права, схема результата LLM | появится позже |

Определение ссылается на домен только по именам (событие, команда, роль) и не содержит его структуру.

## Блоки определения

| Блок | Назначение | Обязателен |
|---|---|---|
| `process` (id, name, version) | идентификация | да |
| `passport` | цель, **владелец**, границы, KPI | да (`owner`) |
| `roles` | роли и ответственности, `kind`: human / system / ai | да |
| `data` | поля процесса: тип, источник, обязательность | да |
| `rules` | реестр правил с версией | нет |
| `states` | состояния: тип, финальность, SLA, распределение работы | да |
| `transitions` | переходы: триггер, условие, роль, действие, `ruleRefs`, `journal` | да |
| `timers` | дедлайны состояний | нет |
| `forbidden` | явные запреты переходов | нет |
| `agent` | источники, стоп-условия, запреты для LLM-шагов | нет |
| `tests` | декларативные сценарии «дано — когда — тогда» | нет |
| `audit` | что писать в журнал | нет |

### Правила и условия

Условия остаются inline (`condition`), а `ruleRefs` связывает переход с правилом из `rules` для версионирования и аудита. Движок правила не вычисляет — только фиксирует ссылку.

### Таймеры и переходы

Таймер объявляет только дедлайн (`id`, `state`, `at`). Развилка выражается переходами с `on.timer` и условиями — одно правило в одном месте.

## Версионирование

- `schemaVersion` — версия контракта. Несовместимое изменение — новая версия схемы.
- `version` внутри определения — версия процесса, фиксируется при запуске инстанса.
- Правила (`rules[].version`) версионируются отдельно от процесса.
- Старые определения не переписываются под новую схему.

## Валидация

Полная проверка требует `jsonschema`; без него выполняется только семантическая проверка.

```bash
cd ../tribe-engine
python3 scripts/validate_process_definitions.py
```

Проверяется:

- соответствие JSON Schema;
- `schemaVersion`, наличие и существование `passport.owner`;
- ссылки на роли и правила;
- уникальность идентификаторов;
- существование состояний в переходах, таймерах и запретах;
- наличие триггера у каждого перехода;
- достижимость состояний и наличие финальных;
- цели декларативных тестов.

## Связь с Process IR

Схема совместима по смыслу с Process IR (AI Process Architect), но проще и объекто-центрична: только то, что нужно для исполнения. Моделирование остаётся в конструкторе, исполнение — в движке.

Сознательно не берём из IR: `steps`/`edges` (блок-схема), `automationHint` и `customLogic` (привязка к n8n), `readiness` и `classification` (дизайн-состояние).
