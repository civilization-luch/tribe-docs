# Движок процессов (Process Engine)

Исполняет декларативные процессы: состояния, переходы, ожидания, задачи людям,
таймеры. Процесс описывает **жизненный цикл объекта** (закупка, сделка, заявка на
расход, предложение) и отвечает на вопрос «кто кому что должен и к какому сроку».
Факты и инварианты остаются в агрегатах.

Код: `src/tribe_process` (ядро, без знания о домене) и `src/tribe_engine/process`
(адаптер: роли, уведомления, действия, хранилище). Определения —
`tribe-docs/schemas/process-engine`.

## Когда заводить процесс

Процесс оправдан, если выполняется **минимум два** условия:

1. больше одного актора с передачей работы;
2. есть ожидание — дедлайн, ответ второй стороны, внешнее событие;
3. есть деньги или обязательство, за которое кто-то отвечает;
4. порядок должен настраиваться сообществом, а не релизом;
5. важен путь, а не только финальный статус.

Не заводим: комментарии, уведомления, посты, сессии, задачи на доске. Это записи,
а не жизненные циклы: инстанс на комментарий — тысячи строк и ноль решений.

## Модель

| Слой | Отвечает за |
|---|---|
| **Агрегат** | факты, инварианты, статус. «Нельзя одобрить дважды» живёт здесь |
| **Процесс** | очерёдность, сроки, кто чего ждёт. Решения и переходы |
| **Домен ↔ процесс** | команды с `via_process`, события в журнал |

Один инстанс — **на агрегат-контекст**, не на человека. Группа влияет только на
«кто» (исполнитель, уведомление, кворум), но не на «сколько».

Разбиение на участников делает домен: закупка создаёт сделку на каждого участника,
каждая сделка запускает свой процесс по событию `DealProposed`.

## Формат определения (schemaVersion 0.4)

```json
{
  "schemaVersion": "0.4",
  "id": "treasury.expense",
  "name": "Расход из казны",
  "version": "2026-11-03",
  "contextType": "treasury_transaction",
  "host": { "module": "treasury", "stateMap": { "pending_approval": "approval" } },
  "passport": { "owner": "treasurer", "goal": "...", "startsWhen": "...", "endsWhen": "..." },
  "roles": [ ... ],
  "data": [ ... ],
  "elements": { ... },
  "transitions": [ ... ],
  "timers": [ ... ],
  "tests": [ ... ]
}
```

### Элементы

| Тип | Смысл |
|---|---|
| `startEvent` | вход в процесс |
| `endEvent` (`final: true`) | финал; инстанс завершается |
| `userTask` | задача человеку: роль, `timing.sla`/`reminder`, `decisions` |
| `serviceTask` | автоматическое действие без человека (`action` + `args`) |
| `intermediateCatchEvent` | ожидание события или таймера |
| `exclusiveGateway` | условие: одна из ветвей должна совпасть |
| `eventBasedGateway` | ожидание одного из событий |

`parallelGateway` объявлен в типах, но **не поддерживается** машиной.

### Переходы

```json
{ "id": "tr_reject", "from": "after_approval", "to": "rejected",
  "condition": { "all": [ { "field": "last_decision", "op": "==", "value": "reject" } ] },
  "actions": [ { "action": "treasury_reject_expense",
                 "args": { "expense_id": "${context_id}", "via_process": true } } ],
  "notify": [ { "to": "role:requester", "title": "Расход отклонён", "body": "..." } ],
  "actorMode": "system", "label": "отклонить" }
```

Правила, которые проверяет валидатор:

- из одного состояния нельзя два перехода с одним и тем же триггером — развилка
  оформляется ромбом;
- у задачи с `decisions` ровно один переход без триггера, ведущий в ромб, и у ромба
  ветви на каждое решение;
- у `exclusiveGateway` каждая исходящая ветвь имеет условие;
- у состояния не бывает двух переходов с одинаковым `on.event`/`on.timer`;
- условия на события домена должны ссылаться на `event.aggregate_id` контекста —
  иначе чужое событие сдвинет инстанс.

### Роли

| Объявление | Кто получит задачу |
|---|---|
| `assigneeField: "created_by"` | значение поля у контекста |
| `assigneeFields: ["a", "b"]` | несколько полей |
| `groupSetting: "wallet.accountant_group_id"` | участники группы из настроек сообщества |
| `capability: "treasury.operate"` + `scopeField: "treasury_id"` | те, у кого есть право в этом скоупе |

`scopeField` разрешается через один уровень: если по полю лежит не группа, а объект
с `group_id` (казна), берётся его группа.

Уведомления адресуются так же: `to: "role:<id>"` резолвится тем же кодом, что и
исполнители. `context_owner` — поле `user_id` у контекста, `owner` — владелец
сообщества, `actor` — последний действовавший.

### Host

`host.module` — модуль-хозяин: процесс казны требует включённый модуль «Казна».
`stateMap` связывает статус агрегата с состоянием процесса для UI. `contextUrl`,
`contextLabel`, `contextPreview` — как показать объект в карточке задачи.

## Исполнение

1. Доменное событие приходит в журнал.
2. Раннер находит определения, которые слушают это событие.
3. Инстанс стартует (если ещё не стартовал для этого контекста) или продвигается.
4. Переход выполняет `actions` через `CommandProcessor`, затем меняет состояние,
   затем шлёт `notify`.
5. Задачи с открытой `userTask` ждут решения; решение закрывает задачу и двигает
   процесс.

Свойства:

- **атомарность** — переход, действия и сохранение инстанса в одной транзакции;
- **идемпотентность** — повторное событие не перезапускает уже выполненные
  обработчики;
- **таймеры** — отдельный воркер раз в минуту; дедлайн задаётся либо `timing.deadline`
  (часы от входа), либо `${переменная}` с ISO-датой;
- **событие может прервать задачу** — отмена заявки закрывает открытую задачу;
- **тупик виден** — `exclusiveGateway` без совпавшей ветви переводит инстанс в
  `failed` с причиной, а не оставляет его молча стоять.

## Контракт с доменом

Действия, которые принимает решение, объявляются с `via_process: true` и без него
отказывают:

```python
if not args.get("via_process"):
    raise Exception("Расходом управляет процесс")
```

Обратный случай — `require_no_process`: прямое действие запрещено, пока по объекту
открыт процесс.

Процессы слушают только **публичные события** из
`tribe-docs/schemas/events/public_events.json`. Валидатор падает, если процесс
ссылается на событие вне контракта или читает необъявленное поле payload.

События приходят в контекст сообщества: `CommandProcessor` требует `community_id`
для community-скоуп модулей и умеет брать его из аргументов действия
(`community_id`) или из сущности, объявленной в `ModifierBase.community_args`.

## Версии и снапшоты

- файл — источник истины для текущей версии;
- при старте каждая версия сохраняется снапшотом в `entities` (`process_definition`);
  инстанс, привязанный к старой версии, продолжает резолвиться;
- изменить содержимое, не подняв `version`, нельзя — старт упадёт с
  `changed without a version bump`;
- архивные определения старой схемы пропускаются с предупреждением.

## Раннер

`SubscriptionRunner` — журнальный диспетчер в процессе API, не шина:

- один курсор на кластер, `pg_try_advisory_lock` держит одна реплика, вторая ждёт;
- at-least-once: обработчик может выполниться повторно, действия должны быть
  идемпотентны;
- ошибки бизнес-уровня (`ValueError`, `PermissionError`) сразу уходят в
  `event_failures` — ретраить правило домена бессмысленно; неожиданные сбои
  ретраятся с backoff;
- heartbeat раз в 10 секунд, даже когда событий нет.

## Наблюдение

| Сигнал | Что значит |
|---|---|
| `process_definitions` в `/health` | определения загружены (0 — папка не смонтирована) |
| `runner_age_seconds` в `/health` | сколько секунд назад раннер подавал признак жизни |
| `process health: {...}` раз в 5 минут | снимок: определения, канарейка, упавшие инстансы, dead-letter, лаг |
| канарейка `system.canary` | двигает определение через машину в памяти; ловит поломку без трафика |

Канарейка и heartbeat не зависят от нагрузки; `failed_instances` и `dead_letters`
заполняются только при реальной работе и алертят при значении больше нуля.

## Деплой

Определения живут в `tribe-docs` и монтируются в api как `/docs:ro`:

```
~/apps/tribe-docs    # рядом с ~/apps/tribe и ~/apps/tribe-dev
TRIBE_PROCESS_DEFINITIONS_DIR=/docs/schemas/process-engine/examples
```

Обновление — два шага, потому что реестр читается при старте:

```bash
make deploy-docs-pull
make deploy-api          # или restart api на dev
```

## Как добавить процесс

1. Описать жизненный цикл: состояния, кто чего ждёт, чем заканчивается.
2. Проверить, что домен хранит факты и инварианты, а процесс — только очерёдность.
3. Написать определение в `schemas/process-engine/examples/`.
4. Добавить действия в модификатор с `via_process` и (при необходимости)
   `require_no_process` для прямого пути.
5. Добавить события в `public_events.json` с полями payload, которые читает процесс.
6. Запустить `python scripts/validate_process_definitions.py` — схема, правила и
   контракт событий.
7. Добавить декларативные `tests` в определение — они прогоняются в CI.
8. Проверить на локальном стенде живой сценарий, затем на dev.

## Ограничения

- **multi-instance** («этот шаг каждому участнику») не поддерживается: нет
  fan-out и агрегации «все ответили»;
- `parallelGateway` не реализован;
- видимость инстансов — по назначению и роли, не по группе;
- таймеры проверяются раз в минуту, точность — до минуты;
- раннер один на кластер; при росте нагрузки нужен шардинг по сообществам.
