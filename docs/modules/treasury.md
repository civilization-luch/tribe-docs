# Модуль Treasury

Казна, бюджеты, финансовая прозрачность.

## Сущности

- **Fund** — фонд/касса (общий, резервный, на мероприятия)
- **Budget** — бюджет на период
- **Transaction** — приход/расход
- **Category** — статья расходов (коммуналка, ремонт, уборка, ивенты)
- **Balance** — баланс участника

## Actions

| Action | Описание |
|---|---|
| `create_fund` | Создать фонд |
| `deposit` | Пополнить казну |
| `withdraw` | Списать из казны |
| `set_budget` | Установить бюджет |
| `get_balance` | Баланс участника |
| `get_report` | Отчёт за период |
| `audit` | Аудит казны |

## Фонды

| Фонд | Назначение |
|---|---|
| Общий | Коммуналка, аренда, базовые расходы |
| Резервный | Непредвиденные траты |
| Мероприятия | Еда, декор, ивенты |
| Ремонт | Мебель, ремонт, обновления |

## Прозрачность

Все транзакции видны всем участникам сообщества (или группе дома). Участник может в любой момент посмотреть, куда пошли деньги.

## Примеры для кейсов

| Продукт | Фонды |
|---|---|
| **CoLive** | Коммуналка, ремонт, мероприятия, резерв |
| **CoSpace** | Аренда зала, инвентарь, маркетинг, ремонт |
| **CoSettle** | Земля, стройка, инфраструктура, резерв |
| **CoGuild** | Гранты на проекты, ивенты, инструменты |
| **CoOper** | Закупки, распределение прибыли, резерв, развитие |

## Операции казны

Каждая проводка описывает не только сумму, но и то, как деньги реально двигались.

| Поле | Значение |
|---|---|
| `type` | `deposit` — поступление, `withdrawal` — выдача |
| `method` | `bank`, `cash`, `crypto`, `other` |
| `custodian_id` | кто физически принял наличные (обязателен для cash-поступления) |
| `recipient` | кому выданы деньги (обязателен для любой выдачи) |
| `doc_number` | номер платёжного поручения (обязателен для `bank`) |
| `doc_date` | дата документа в ISO (обязательна для `bank`) |
| `reference` | хеш транзакции для крипты, произвольная ссылка для остальных методов |
| `description` | свободный комментарий |
| `created_by` | кто провёл операцию |

## Наличные

- Наличное поступление нельзя провести без держателя: деньги в базе должны иметь физический адрес.
- Наличная выдача требует получателя, иначе непонятно, кому отдали.
- Для наличных платёжное поручение не нужно: доказательство — расписка, приложенная файлом.
- Баланс казны считается отдельно по каждому методу: «на счету» и «наличными на руках».

## Доказательство перевода

Требования зависят от метода — обязательное встречное подтверждение нужно только там, где нет внешнего регистратора.

| Метод | Обязательные реквизиты | Артефакт |
|---|---|---|
| `bank` | `doc_number` + `doc_date` | выписка или платёжка — по желанию |
| `cash` | держатель при поступлении, получатель при выдаче | расписка файлом |
| `crypto` | хеш транзакции | скрин эксплорера — по желанию |
| `other` | — | — |

Доказательство хранится вложением, а не строкой:

- файл привязывается к конкретной заявке или проводке, формат — JPEG, PNG или PDF, размер до 10 МБ;
- доступ только у участников перевода и ответственных (бухгалтеры казны, операторы гарантий, админ сообщества); ссылки короткоживущие, скачивания фиксируются;
- `sha256` файла пишется в событие, поэтому подмена обнаруживается;
- срок хранения — 5 лет с даты операции (настройка сообщества `treasury.receipt_retention_years`); пока идёт спор или операция не закрыта, удаление заблокировано;
- истечение срока оформляется событием `AttachmentPurged`: файл стирается, метаданные остаются.

## Единое доказательство

Реквизиты, артефакт и подтверждения теперь описываются одним объектом `TransferEvidence`: стороны (`person` / `community` / `platform`), способ расчёта (`external_direct` / `platform_ledger` / `none`), направление, метод, сумма, реквизиты, вложения и подписи с ролями.

Минимум подписей зависит от пары «стороны + способ»: для гарантии — отправитель и получатель, для казны — бухгалтер, для наличной выдачи — бухгалтер и получатель. Внутренний перевод между счетами помечается `none` и не требует ничего.

Старые поля (`reference`, `proof`, `doc_number`, `doc_date`, `payout_reference`) остаются в схеме для обратной совместимости, но помечены устаревшими: чтение идёт через `evidence`. Исторические записи восстановлены скриптом `scripts/backfill_transfer_evidence.py` с пометкой `origin=backfill`; подписи восстанавливались только там, где исполнитель известен.

## Права

Пополнять казну может участник сообщества. Списывать — только владелец, админ или участник группы бухгалтеров (`wallet.accountant_group_id`).

## Взносы участников

Заявка на пополнение может быть зачислена:

- на личный баланс участника (по умолчанию);
- сразу в казну сообщества;
- в бюджет конкретной группы.

При подтверждении бухгалтер видит, куда пойдут деньги; валюта заявки должна совпадать с валютой казны.

## Движение средств (сверка)

Единый список объединяет проводки казны и заявки участников.

- `source` у проводки: `manual` — провёл человек, `wallet:<user>` — перевод с баланса, `claim:<id>` — подтверждённая заявка.
- `review` у записи подсвечивает то, что требует внимания:
  - `pending` — заявка ждёт подтверждения;
  - `no_reference` — банковское поступление без ссылки на платёж;
  - `duplicate_reference` — одна ссылка встречается в нескольких поступлениях;
  - `no_treasury_entry` — заявка с целевым счётом подтверждена, но проводки в казне нет.

Правило: каждая реальная проводка должна иметь одну запись с назначением. Если участник сначала положил деньги на баланс, а затем перевёл в казну — это две внутренние операции, связанные источником.

## Валюты сообщества

Сообщество ведёт список валют и одну основную:

- **фиат** — KZT, USD, EUR, RUB и другие;
- **крипта** — USDT, USDC, BTC, ETH;
- **внутренние единицы** — `POINT`: не выводятся наружу, эмитируются внутри сообщества, служат для расчётов и гарантий.

Правила:

- неизвестный код отклоняется при сохранении — опечатка не должна создавать отдельный учёт;
- основная валюта всегда входит в список;
- кошельки и казённые счета создаются в валюте сообщества;
- конвертации между валютами нет: пересчёт только отчётный, с пометкой «оценка».

Внутренние единицы не являются деньгами на счёте: это обязательство сообщества, и в интерфейсе они помечаются отдельно.

## Крипто-пополнения (без интеграции с блокчейном)

Пока нет API к сетям, крипта принимается тем же ручным способом, что и банковский перевод.

1. Админ сообщества задаёт реквизиты в казне: сеть, актив, адрес. На сообщество — один активный адрес; пользователь выбирает его из формы и не может вписать свой.
2. Участник создаёт заявку: метод `crypto`, сумма, **хеш транзакции обязателен**.
3. Бухгалтер проверяет в эксплорере сеть, актив, сумму, получателя и число подтверждений, затем подтверждает.
4. Подтверждённая заявка создаёт проводку казны `method=crypto`, `reference=<tx hash>`, `source=claim:<id>`.

Сверка: крипто-поступление без хеша флагуется как `no_reference`, повтор одного хеша — `duplicate_reference`.

Ограничение: платформа не проверяет транзакцию автоматически; ответственность за проверку лежит на бухгалтере.

## Возврат с баланса

Участник может вывести деньги с личного баланса; операцию подтверждает бухгалтер.

1. Участник создаёт заявку на вывод: сумма, метод (`bank` / `crypto` / `cash`), реквизиты, комментарий. Сумма не может превышать баланс.
2. Бухгалтер проверяет реквизиты и подтверждает, указав номер платежа или хеш перевода; без ссылки подтверждение не проходит.
3. Подтверждение списывает сумму с баланса (`entry_type=refund`) и фиксирует `payout_reference`.
4. Отклонение не меняет баланс; участник получает причину.

Заявки видны бухгалтеру в казне и в общем движении средств (`kind=refund`, направление «расход»). Подтверждённый вывод без ссылки на платёж флагуется как `no_reference`.

Ограничение: платформа не отправляет деньги сама — выплату делает бухгалтер, система фиксирует факт и доказательство.
